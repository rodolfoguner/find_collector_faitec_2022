# Technical and product roadmap

The roadmap prioritizes a predictable, testable backend before the frontend is
rebuilt. The order may change, but every phase should end with a green build,
passing tests, and updated documentation.

Planning update: 2026-10-01. The additions below describe future work only;
they do not introduce dependencies, configuration, or implementation changes.
The active baseline is Java 25 and Spring Boot 3.5.16, with the `api`,
`application`, `domain`, and `infrastructure` modules. Actuator and the health
check already exist; they are a foundation for the planned observability work.

### Code quality and security analysis

- [ ] Integrate SonarQube for static analysis of reliability, maintainability,
  and security; import test coverage generated by JaCoCo and define a quality
  gate for new code.
- [ ] Integrate Snyk Code for static application security testing (SAST) of
  source code.
- [ ] Integrate Snyk Open Source for software composition analysis (SCA),
  covering vulnerabilities in direct and transitive Maven dependencies and
  license-policy compliance across the active modules.
- [ ] Triage the initial findings, define CI blocking criteria, and record
  exceptions with an owner, justification, and expiration date. Coordinate
  overlapping SonarQube and Snyk Code findings to avoid duplicate remediation.
- [ ] Confirm supported languages and required features in the selected tool
  editions/plans, store credentials in CI secrets, and retain analysis reports.

SonarQube evaluates code quality and security; Snyk Code focuses on source-code
vulnerabilities, while Snyk Open Source evaluates dependencies. SonarQube imports
coverage reports rather than running tests to generate coverage. Integrations
should follow a reproducible build/test pipeline; initial analysis can establish
a baseline before blocking criteria are enabled.

**Completion criteria:** reports cover the relevant active modules, test
coverage is imported, and CI enforces the agreed quality and security gates.

## Authentication and accounts

- [x] Implement Spring Security for the API.
- [x] Define and implement access and refresh tokens.
- [x] Persist login sessions in PostgreSQL, rotate refresh tokens once per use,
  revoke sessions on refresh reuse, and invalidate access and refresh tokens on
  current-session logout.
- [x] Add an endpoint for the authenticated user.
- [ ] Define an operation-level permission matrix for `RECYCLER` and
  `COLLECTOR`, distinguishing authentication from authorization.
- [ ] Implement role-based access control (RBAC) with Spring Security to
  restrict operations by role.
- [ ] Complement RBAC with attribute-based access control (ABAC), checking
  resource ownership, collection participation, and `CollectStatus` as required
  by each operation. Require both an allowed role and valid attributes.
- [ ] Deny access by default and enforce authorization at API boundaries and
  application use cases, keeping business policies out of controllers and
  persistence adapters and framework-specific dependencies out of `domain`.
- [ ] Derive identity and roles from validated authentication and load resource
  attributes on the server; reject attempts to gain access by changing IDs,
  ownership fields, or roles in request payloads. Apply policies to list results
  as well as individual reads and writes.
- [ ] Add positive and negative authorization tests for anonymous access,
  incorrect roles, the correct role without ownership/participation, forged
  attributes, and direct API calls. Preserve the standardized error contract
  when handling authentication and authorization failures.
- [ ] Audit relevant authorization decisions with minimal identifiers, result,
  reason, operation, timestamp, and trace correlation when available; restrict
  access and define retention for audit records.
- [ ] Require account activation through a short-lived email verification token.
- [ ] Enforce a documented password-strength policy in the API and mirror its
  feedback in the frontend.
- [ ] Implement password changes.
- [ ] Implement account recovery through a verified email address or phone
  number, using single-use, short-lived tokens to reset the password.

The initial policy should allow editing only one's own profile, restrict
collection publication to recyclers, and restrict acceptance to collectors
when the collection is `PENDING` and available. Cancellation and completion
require an allowed role, a valid relationship to the collection, and an allowed
`CollectStatus` transition; their exact permissions must be defined alongside
the lifecycle rules. Public discovery and private participant details need
separate read policies. Hiding frontend controls does not enforce authorization.

**Completion criteria:** tests demonstrate both permitted and denied operations,
including attempts to access another user's resources; denied writes leave
data unchanged. Authentication and explicit lifecycle policies are prerequisites
for validating the complete access model.

## Observability: logging, metrics, and tracing

### Logging with SLF4J and Logback

- [ ] Standardize application logging through the SLF4J API and Logback,
  building on the logging support supplied by Spring Boot starters.
- [ ] Define structured output, levels by environment, service identification,
  and retention; log relevant failures and application events without passwords,
  tokens, or unnecessary personal data.
- [ ] Correlate logs with `traceId` and `spanId` when tracing context is available.

**Completion criteria:** controlled failures generate useful, consistently
formatted logs; environment settings and retention are documented, and trace
correlation is verified once tracing is configured.

### Metrics with Actuator, Micrometer, and Prometheus

- [ ] Extend the existing Actuator foundation with Micrometer metrics for HTTP
  traffic, errors, latency, JVM behavior, and collection use cases.
- [ ] Add the Prometheus registry and configure Prometheus to scrape the API's
  `/actuator/prometheus` endpoint.
- [ ] Keep labels bounded in cardinality; avoid user/collection IDs, personal
  data, and raw URLs containing resource IDs.
- [ ] Restrict management endpoint exposure and permit scraping only from
  authorized infrastructure, independently of business-user roles.
- [ ] Document initial queries and alert conditions; set operational targets
  after measuring a baseline.

Actuator supplies management integration and endpoints; Micrometer instruments
and records measurements; Prometheus collects and stores metric time series.
An existing health check does not mean that Prometheus collection is configured.
See the [Spring Boot 3.5 metrics documentation](https://docs.spring.io/spring-boot/3.5/reference/actuator/metrics.html).

**Completion criteria:** Prometheus successfully scrapes the API, test traffic
changes the expected metrics, and unauthorized management access is denied.

### Tracing with Micrometer and OpenTelemetry

- [ ] Integrate Micrometer Observation/Tracing with the OpenTelemetry bridge
  and an OTLP exporter, using dependencies compatible with the active Spring
  Boot platform.
- [ ] Trace inbound API requests and relevant application/persistence
  operations; propagate context through instrumented outbound HTTP clients
  when integrations are added.
- [ ] Select a backend for trace storage and querying; evaluate an
  OpenTelemetry Collector if centralized processing and forwarding are needed.
- [ ] Define sampling, retention, and sensitive-data filtering; verify log
  correlation and avoid duplicate instrumentation of the same operation.

Prometheus handles metrics in this design. Traces require a separate backend;
the OpenTelemetry Collector processes and forwards telemetry rather than
replacing trace storage. Tracing concerns should respect module boundaries
without coupling the domain model to observability frameworks. See the
[Spring Boot 3.5 tracing documentation](https://docs.spring.io/spring-boot/3.5/reference/actuator/tracing.html).

**Completion criteria:** a test request has queryable spans in the chosen
backend and corresponding logs can be found by trace ID. This depends on a
selected export destination and the logging foundation, not on rebuilding the
legacy frontend.

- [ ] Configure authenticated scans for recycler and collector accounts and

- [ ] Begin with passive analysis and enable active scanning in the authorized

- [ ] Retain and review reports, and complement scans with targeted RBAC/ABAC

**Completion criteria:** authenticated scans cover both roles, reports are
reviewed, and agreed findings block CI or release validation. This requires a
running test environment and usable authentication/authorization. DAST and
static analyzers complement, rather than replace, tests of business permissions.

## Frontend

The frontend technology will be selected after the API has authentication,
stable contracts, complete OpenAPI documentation, pagination, and a defined
error format. The client under `legacy/` is only a reference for journeys,
content, and visual elements; it is not a required foundation for the new
implementation.

The frontend scope should include educational content explaining recyclable
material types, separation practices, preparation for collection, and correct
disposal. This content should be designed together with the new frontend so it
is accessible in the relevant user journeys instead of being coupled to the
backend domain model.
